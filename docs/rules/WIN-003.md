# WIN-003 同一送信元・利用者への認証失敗集中

- 状態：experimental / 重要度：medium
- SIEM：Splunk Enterprise / Splunk Cloud Platform (SPL)
- 対象ログ：windows

## MITRE ATT&CK Matrix上の位置

|戦術（Matrixの列）|親技法|サブ技法|本ルールとの関係|
|---|---|---|---|
|[TA0006 Credential Access](https://attack.mitre.org/tactics/TA0006)|[T1110 Brute Force](https://attack.mitre.org/techniques/T1110)|[T1110.001 Password Guessing](https://attack.mitre.org/techniques/T1110/001)|主な検知仮説|

同一host・送信元・利用者への5分10回以上の4625をPassword Guessing候補とする。パスワード値や侵入成功はログから判定しない。

[リポジトリ全体のマトリクス](../matrix.md)。これは技法の一部に対する検知仮説で、技法全体のカバレッジではありません。

## 対象ログ・必要フィールド

- 検知に必須：`_time`, `channel`, `event_id`, `host`, `log_type`, `src_ip`, `user`
- 調査に推奨：`event_id`, `src_ip`, `user`, `TargetDomainName`, `Status`, `SubStatus`, `LogonType`, `AuthenticationPackageName`, `WorkstationName`

Audit Logon Failure。IpAddressとTargetUserNameを正規化。重複イベントを除去。

型・元項目・欠損監視は[フィールド定義](../log-sources.md)を参照。推奨項目が未採取の場合は調査結果に制約を記録します。

## 検知条件

`=` は一致、`~=` は正規表現一致、`>=` は以上、`AND` はすべて満たす意味です。`dc()` は異なる値の数です。`~=` は説明・JSON定義の記号で、SPL本文では `match()` に変換します。必須フィールドがNULLなら対象外です。

```text
log_type = "windows"
AND channel = "Security"
AND event_id = 4625
AND src_ip ~= /^(?!-$).+/
AND user ~= /^(?!-$).+/

GROUP BY host, src_ip, user
WINDOW = 300 seconds
count(*) >= 10
```

## 検知SPL（Splunk）

`index=detection_lab` を正規化済みログのindexに変更してください。5分間隔、5分遅延の検索を想定しています。生ログにそのまま適用せず[Splunk導入手順](../deployment.md)でフィールドを確認してください。

```spl
index=detection_lab log_type="windows" earliest=-10m@m latest=-5m@m
| where isnotnull(_time)
    AND isnotnull(channel)
    AND isnotnull(event_id)
    AND isnotnull(host)
    AND isnotnull(log_type)
    AND isnotnull(src_ip)
    AND isnotnull(user)
    AND channel="Security"
    AND event_id=4625
    AND match(src_ip, "^(?!-$).+")
    AND match(user, "^(?!-$).+")
| stats count as observed min(_time) as first_seen max(_time) as last_seen by host src_ip user
| where observed >= 10
| eval rule_id="WIN-003", attack_id="T1110.001"
```

## 誤検知とチューニング

古いパスワードのサービス、入力ミス、共有NAT。

## 調査手順・判断基準

1. 対象host・src_ip・userの前後15分を検索し、4625のStatus/SubStatus、LogonType、AuthenticationPackageName、WorkstationNameを確認する。誤パスワード、存在しないユーザー、ロックアウト等を分ける。

2. 5分窓内の発生間隔と生イベント数を確認する。同一レコードの重複転送、サービスの一定周期リトライ、NAT後の複数端末集約が件数を増やしていないかを調べる。

3. 同じ送信元の他ユーザー・他宛先への失敗も展開し、一人への推測かパスワードスプレーかを判別する。TargetDomainNameも確認し、同名ローカルユーザーとドメインユーザーを混同しない。

4. 後続30分の4624、4740と、収集済みならDCの4771/4776を照合する。成功イベントは送信元・対象ユーザー・認証方式・ログオン種別を比較し、同一人物の成功と自動的に断定しない。

5. サービス所有者へ資格情報更新・ジョブ障害の有無を確認する。未承認送信元や失敗後の成功と不審操作がある場合は、該当アカウント・送信元・成功セッションの証拠を添えて調査を引き継ぐ。

### 調査SPL：元イベントの時系列

`REPLACE_...` を検知結果の集約キーに置換します。過去アラートでは `earliest` / `latest` を発生時刻の前後15分の絶対時刻（Unix秒）に変更してください。下記の直近30分は調査開始例です。別ログ種別との照合は対象indexとlog_typeを切り替え、端末IP・host・ユーザーの対応を確認して行います。

```spl
index=detection_lab log_type="windows" host="REPLACE_HOST" src_ip="REPLACE_SRC_IP" user="REPLACE_USER" earliest=-30m@m latest=now
| sort 0 _time
| table _time host log_type channel event_id src_ip user TargetDomainName Status SubStatus LogonType AuthenticationPackageName WorkstationName _raw
```

推奨フィールドが未抽出なら `_raw` を参照します。調査SPLは検知条件を再適用せず、同じキーの正常・異常両方を表示します。キー以外の宛先・利用者へ展開する場合は該当セレクタを外して範囲を広げます。

## 限界・見逃す条件

- 閾値と窓：5分10回未満、窓境界に分割された失敗、複数送信元を使う試行は取りこぼす。基準値を実ログで決め、低速攻撃には長窓の別ルールを用意する。

- 認証経路：4625以外の4771/4776やクラウド認証だけの失敗は対象外。Windows全認証のブルートフォース検知とは扱わない。

- 帰属：IpAddressが空または「-」なら対象外。localhost、NAT、認証ゲートウェイのIPは端末本人を示さない場合がある。DHCP・VPN・ゲートウェイログで補完する。

- ユーザー区別：現行キーはhost/src_ip/userで、TargetDomainNameを含まない。同じ端末の同名ユーザーが異なるドメインに存在する環境ではuserをドメイン付きに正規化するか集約キーを変更して再検証する。

共通制約：固定5分窓をまたぐ閾値未満の分散、5分を超える収集遅延、必須フィールド欠損、重複転送の影響を評価してください。Splunk上の実ログ検証・PCRE評価は未実施で、合成テストの成功は本番検知率を示しません。
