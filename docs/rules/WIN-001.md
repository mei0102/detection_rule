# WIN-001 EncodedCommandを使うPowerShell

- 状態：experimental / 重要度：medium
- SIEM：Splunk Enterprise / Splunk Cloud Platform (SPL)
- 対象ログ：windows

## MITRE ATT&CK Matrix上の位置

|戦術（Matrixの列）|親技法|サブ技法|本ルールとの関係|
|---|---|---|---|
|[TA0002 Execution](https://attack.mitre.org/tactics/TA0002)|[T1059 Command and Scripting Interpreter](https://attack.mitre.org/techniques/T1059)|[T1059.001 PowerShell](https://attack.mitre.org/techniques/T1059/001)|主な検知仮説|

4688の実行ファイル名とEncodedCommand系引数から、PowerShellによるスクリプト実行の候補を観測する。エンコード内容の悪性や実行成功は判定しない。

[リポジトリ全体のマトリクス](../matrix.md)。これは技法の一部に対する検知仮説で、技法全体のカバレッジではありません。

## 対象ログ・必要フィールド

- 検知に必須：`_time`, `channel`, `command_line`, `event_id`, `host`, `log_type`, `process_path`
- 調査に推奨：`SubjectUserName`, `SubjectLogonId`, `NewProcessId`, `CreatorProcessId`, `ParentProcessName`, `command_line`, `process_path`

Audit Process CreationとInclude command line in process creation eventsを有効化。

型・元項目・欠損監視は[フィールド定義](../log-sources.md)を参照。推奨項目が未採取の場合は調査結果に制約を記録します。

## 検知条件

`=` は一致、`~=` は正規表現一致、`>=` は以上、`AND` はすべて満たす意味です。`dc()` は異なる値の数です。`~=` は説明・JSON定義の記号で、SPL本文では `match()` に変換します。必須フィールドがNULLなら対象外です。

```text
log_type = "windows"
AND channel = "Security"
AND event_id = 4688
AND process_path ~= /(?i)(^|[\\/])(powershell|pwsh)\.exe$/
AND command_line ~= /(?i)(^|\s)-(e|en|enc|enco|encod|encode|encoded|encodedc|encodedco|encodedcom|encodedcomm|encodedcomma|encodedcomman|encodedcommand)\s+\S+/

GROUP BY host
WINDOW = 300 seconds
count(*) >= 1
```

## 検知SPL（Splunk）

`index=detection_lab` を正規化済みログのindexに変更してください。5分間隔、5分遅延の検索を想定しています。生ログにそのまま適用せず[Splunk導入手順](../deployment.md)でフィールドを確認してください。

```spl
index=detection_lab log_type="windows" earliest=-10m@m latest=-5m@m
| where isnotnull(_time)
    AND isnotnull(channel)
    AND isnotnull(command_line)
    AND isnotnull(event_id)
    AND isnotnull(host)
    AND isnotnull(log_type)
    AND isnotnull(process_path)
    AND channel="Security"
    AND event_id=4688
    AND match(process_path, "(?i)(^|[\\\\/])(powershell|pwsh)\\.exe$")
    AND match(command_line, "(?i)(^|\\s)-(e|en|enc|enco|encod|encode|encoded|encodedc|encodedco|encodedcom|encodedcomm|encodedcomma|encodedcomman|encodedcommand)\\s+\\S+")
| stats count as observed min(_time) as first_seen max(_time) as last_seen by host
| where observed >= 1
| eval rule_id="WIN-001", attack_id="T1059.001"
```

## 誤検知とチューニング

構成管理・管理者の正規スクリプト。署名、親プロセス、利用者、実行時間を組み合わせて除外する。

## 調査手順・判断基準

1. アラートのhostとfirst_seen/last_seenを起点に前後15分の4688を取得し、CommandLine、NewProcessName、NewProcessId、CreatorProcessId、SubjectUserName、SubjectLogonIdを原文で保存する。PIDは同じhost・近接時刻で照合し、再利用に注意する。

2. 親プロセスがOffice・ブラウザ・一時ディレクトリ由来か、管理エージェントかを確認する。引数のBase64は隔離した解析環境で文字列へ復号し、URL・ファイルパス・追加プロセス起動の有無を調べる。復号した内容は実行しない。

3. 収集済みならPowerShell Operationalの4104をScriptBlockId単位で再構成し、4688の利用者・時刻と照合する。4104がない場合は未実行とせず、Script Block Loggingの収集状態を確認する。

4. 同じ端末のProxy/NDR通信とファイル作成・後続4688を時系列に並べる。IPとの紐付けは当該時刻のDHCP/資産履歴を使う。取得先、保存先、子プロセスが一連の処理かを確認する。

5. 承認済みジョブの所有者・署名・スクリプトハッシュ・実行予定が一致すれば正常候補として記録する。未知の配布元、ユーザー不認知、外部取得と後続実行が重なる場合はインシデント担当へ引き継ぎ、元イベントと復号結果を添付する。

### 調査SPL：元イベントの時系列

`REPLACE_...` を検知結果の集約キーに置換します。過去アラートでは `earliest` / `latest` を発生時刻の前後15分の絶対時刻（Unix秒）に変更してください。下記の直近30分は調査開始例です。別ログ種別との照合は対象indexとlog_typeを切り替え、端末IP・host・ユーザーの対応を確認して行います。

```spl
index=detection_lab log_type="windows" host="REPLACE_HOST" earliest=-30m@m latest=now
| sort 0 _time
| table _time host log_type channel event_id SubjectUserName SubjectLogonId NewProcessId CreatorProcessId ParentProcessName command_line process_path _raw
```

推奨フィールドが未抽出なら `_raw` を参照します。調査SPLは検知条件を再適用せず、同じキーの正常・異常両方を表示します。キー以外の宛先・利用者へ展開する場合は該当セレクタを外して範囲を広げます。

## 限界・見逃す条件

- 観測範囲：powershell.exe/pwsh.exeという名前の4688とASCIIのハイフン引数に限定。実行ファイル名変更、PowerShell APIのインプロセス実行、Unicodeスイッチ、-ecや引用符を使う別表記はこの式では検出しない。

- ログ不足：4688があってもCommandLineが空なら非検知。全4688に対するコマンドライン欠損率を監視し、監査ポリシー・GPO・転送時の切り詰めを確認する。Sysmon Event 1は別途マッピングが必要。

- 特異度：引数の存在だけでBase64の妥当性やスクリプト内容を評価しない。正規の構成管理にも一致するため、PowerShell全体や管理者全体を除外せず、承認済みジョブ単位で調整する。

- 集約：同じhostの5分内実行を1行にまとめるため、observedはアラート件数ではなく一致イベント数。調査SPLで個々のプロセスを確認し、攻撃プロセス数と混同しない。

共通制約：固定5分窓をまたぐ閾値未満の分散、5分を超える収集遅延、必須フィールド欠損、重複転送の影響を評価してください。Splunk上の実ログ検証・PCRE評価は未実施で、合成テストの成功は本番検知率を示しません。
