# WIN-007 認証失敗の集中後に同じ主体がログオン成功

**検知概要：** 同じ端末・接続元・ユーザーでログオン失敗が集中し、その後に成功したケースを探す。

**検知意図：** パスワード試行が成功に至った可能性を調べる。

**過検知予想：** パスワード再入力、保存資格情報の更新。 悪性かどうかは、利用目的や実行主体の確認が必要。

|項目|内容|
|---|---|
|対象ログ|Windows Event|
|必要フィールド|`_time`, `log_type`, `channel`, `event_id`, `host`, `src_ip`, `user`|
|ATT&CK 戦術|[TA0006 Credential Access](https://attack.mitre.org/tactics/TA0006)|
|技法 → サブ技法|[T1110 Brute Force](https://attack.mitre.org/techniques/T1110) → [T1110.001 Password Guessing](https://attack.mitre.org/techniques/T1110/001)|
|検索|15分窓／5分間隔／5分遅延|
|工夫|失敗件数だけでなく、過去10分の失敗→成功という順序を確認。|

## 汎化

- 脅威固有の指標：4625→4624。特定アカウントに依存しない。
- 共通する実装パターン：失敗の集中から同一主体の成功へ遷移。
- 長期利用できる攻撃行動：認証失敗の集中後に同じ主体がログオン成功。特定攻撃者への帰属は行わない。
- 今回採用する条件と理由：同一端末・送信元・ユーザーで、失敗5回以上の後に成功が発生。 この観測範囲で失敗の集中から同一主体の成功へ遷移の候補を抽出するため。
- 採用しない条件と理由：成功のない試行、送信元・ユーザーを変えた成功は今回の条件外。別の観測・検知条件が必要なため、この検索に混在させない。未提供の資産台帳による除外も行わない。

## 検知意図と限界

- 検知できること：同一端末・送信元・ユーザーで、失敗5回以上の後に成功が発生。
- 検知できないこと：同一主体の正常な再入力も一致。成功後の侵害操作までは判定しない。
- 意図的に検知しないこと：成功のない試行、送信元・ユーザーを変えた成功。
- 想定される回避方法：上記の条件外の経路・表記・タイミングへ変更する、または必要ログの記録を妨げる。

## 誤検知

- 主な正常動作：パスワード再入力、保存資格情報の更新。
- 誤検知を識別する追加情報：ログオン種別、成功セッションID、成功後の操作。
- 改善方法：成功セッションに共有アクセスや特権操作を相関。追加情報が取得できる場合の案で、今回のSPLには未適用。
- 除外が必要な場合の対象と根拠：パスワード再入力、保存資格情報の更新のうち、上記情報と承認記録で一致を確認した主体・対象・時間帯だけ。現時点の除外はなし。
- 改善により新たに生じる検知漏れ：承認済み主体の侵害を除外する恐れ。追加条件を必須にすると、正常判別用の証拠が欠落した攻撃も見逃す。

## SPL

- 現行SPL：変更前のリポジトリ版（`5d42ac6`）。顧客環境の稼働版ではない。

<details>
<summary>現行SPLを表示</summary>

```spl
index=detection_lab log_type="windows" earliest=-20m@m latest=-5m@m
| where channel="Security" AND event_id IN (4624,4625)
    AND src_ip!="-" AND user!="-"
| sort 0 _time
| streamstats time_window=10m current=f
        count(eval(event_id=4625)) as prior_failures
        max(eval(if(event_id=4624,_time,null()))) as previous_success
        min(eval(if(event_id=4625,_time,null()))) as first_failure
    by host src_ip user
| where event_id=4624 AND prior_failures >= 5
    AND first_failure > coalesce(previous_success,0)
    AND _time >= relative_time(now(),"-10m@m")
| table _time host src_ip user prior_failures first_failure
| eval rule_id="WIN-007", attack_id="T1110.001"
```

</details>

- 提案SPL：検知条件を維持し、ES設定用の出力列を追加。

```spl
index=detection_lab log_type="windows" earliest=-20m@m latest=-5m@m
| where channel="Security" AND event_id IN (4624,4625)
    AND src_ip!="-" AND user!="-"
| sort 0 _time
| streamstats time_window=10m current=f
        count(eval(event_id=4625)) as prior_failures
        max(eval(if(event_id=4624,_time,null()))) as previous_success
        min(eval(if(event_id=4625,_time,null()))) as first_failure
    by host src_ip user
| where event_id=4624 AND prior_failures >= 5
    AND first_failure > coalesce(previous_success,0)
    AND _time >= relative_time(now(),"-10m@m")
| table _time host src_ip user prior_failures first_failure
| eval rule_id="WIN-007", attack_id="T1110.001"
| eval risk_object=host, risk_object_type="system",
       risk_score=40, severity="medium"
```

- 差分：末尾に`risk_object`、`risk_object_type`、`risk_score`、`severity`を追加。検知件数を変える条件変更はなし。列の追加だけではRiskイベント・Notableは生成されない。
- index、sourcetype、製品固有フィールドの置換箇所：`index=detection_lab`は仮置き。実indexと確認済みsourcetypeへ置換し、`log_type`は共通分類を用意するか実ログ条件へ置換。event_id←EventID、channel←Channel、host←Computer。小文字の共通列とXML原文列の対応は各収集方式で要確認。必要列：`_time`, `log_type`, `channel`, `event_id`, `host`, `src_ip`, `user`。
- 想定負荷：高（全件ソートと時系列状態を保持するため。データ量・同時実行数による概算で未測定）。
- 負荷を抑える工夫：必要イベントをソート前に絞る。検索窓と並列実行数を制限し、streamstatsの上限を確認。CIM対応と加速済みData Modelが確認できる場合のみtstats化を検討。未提供のData Modelは前提にしない。

## Splunk ES設定案

- 実行間隔：5分（設定案）。
- earliest/latest：`-20m@m` / `-5m@m`。取り込み遅延5分を仮定。
- trigger：結果行数 > 0、各結果行を対象。評価後にRisk Analysis等の応答アクションを別途設定。自動のNotable生成は未設定。
- suppression/throttling：初期は無効。重複実績を確認後、同じrule_id・risk_objectの反復を検索窓相当で抑制する案。別対象・別段階まで抑える可能性があるため宛先等の追加キーを評価。
- severity：`medium`（調査優先度の仮案、確信度ではない）。
- risk score：`40`（未検証の相対値）。繰り返し発報と他ルールとの重複加算を評価してから使用。
- risk object／type：`host` → `risk_object` / `system`。出力に残る主体を使用し、資産・ID正規化と共有IPを確認。
- security domain：`access`。
- notable title：`WIN-007 認証失敗の集中後に同じ主体がログオン成功`。Notable化を採用する場合の案。
- drilldown：結果の`host`を元ログの同じ列へ渡し、検知対象窓の前後5分を再検索。ログオン種別、成功セッションID、成功後の操作を表示・照合。未取得の列は追加収集が必要。

## 閾値

- 初期値：同一端末・送信元・ユーザーで、失敗5回以上の後に成功が発生。 数値のないイベント・文字列条件は1件一致で結果候補。
- 根拠：上記行動の候補を切り出す設計値。参照ルールの推奨値や実環境の正常分布を証明する値ではない。
- 高感度設定：失敗3回。記載以外の条件は標準と同じ。SPLには未適用。
- 標準設定：提案SPLの条件。初期値と同一。
- 低誤検知設定：失敗10回（順序条件は維持）。追加情報が必要な案は取得確認が前提で、効果は未確認。
- ベースライン取得方法：30日を同じ検索窓・集約主体`host`で区切り、正常と確認したパスワード再入力、保存資格情報の更新とそれ以外を分け、件数・対象数・数値条件の分布を比較。存在しない統計は補完しない。

## 人が評価すべき点

- 採用判断に必要な確認事項：Windows監査設定・対象イベントの欠落、XML項目の抽出状況。ログオン種別、成功セッションID、成功後の操作で正常業務と識別できるか。
- 不足データ：実index/sourcetype、必要列の充足率、ESバージョン、発報数・TP/FP判定、資産・業務台帳、実行時間。
- 最大のリスク：パスワード再入力、保存資格情報の更新との衝突と、成功のない試行、送信元・ユーザーを変えた成功の取りこぼし。
- 推奨判断：実装候補（本番採用の確定ではない）。
- 推奨理由：観測条件を具体化できるため。必須フィールドと正常業務の識別を確認してから採用を判断する。
