## 対象ログ・必要フィールド

- 検知に必須：`_time`, `channel`, `event_id`, `host`, `log_type`
- 調査に推奨：`event_id`, `TaskName`, `TaskContent`, `SubjectUserName`, `SubjectLogonId`, `ClientProcessId`, `command_line`

Audit Other Object Access Events Success。TaskContent XMLも保存。

型・元項目・欠損監視は[フィールド定義](../log-sources.md)を参照。推奨項目が未採取の場合は調査結果に制約を記録します。

## 検知条件

`=` は一致、`~=` は正規表現一致、`>=` は以上、`AND` はすべて満たす意味です。`dc()` は異なる値の数です。`~=` は説明・JSON定義の記号で、SPL本文では `match()` に変換します。必須フィールドがNULLなら対象外です。

```text
log_type = "windows"
AND channel = "Security"
AND event_id = 4698

GROUP BY host
WINDOW = 300 seconds
count(*) >= 1
```

## 検知SPL（Splunk）

`index=detection_lab` を正規化済みログのindexに変更してください。5分間隔、5分遅延の検索を想定しています。生ログにそのまま適用せず[Splunk導入手順](../deployment.md)でフィールドを確認してください。

```spl
index=detection_lab log_type="windows" earliest=-10m@m latest=-5m@m
| where isnotnull(_time)
    AND isnotnull(channel)
    AND isnotnull(event_id)
    AND isnotnull(host)
    AND isnotnull(log_type)
    AND channel="Security"
    AND event_id=4698
| stats count as observed min(_time) as first_seen max(_time) as last_seen by host
| where observed >= 1
| eval rule_id="WIN-005", attack_id="T1053.005"
```

## 誤検知とチューニング

ソフト更新や運用のタスク登録。高頻度環境ではハンティング用途から開始。

## 調査手順・判断基準

1. 4698のTaskName、TaskContent XML、SubjectUserName、SubjectLogonIdを保存する。TaskContentからActions/ExecのCommand・Arguments・WorkingDirectory、Triggers、PrincipalsのUserId・RunLevelを取り出す。

2. 実行パスがユーザー書込可能なディレクトリ、共有パス、未知のスクリプトを指していないか確認する。引数の外部URL、難読化、署名・ファイルハッシュを調べ、タスクを手動実行しない。

3. 登録者の4624と4688を同じhost・セッション・時刻で関連づけ、配布ツール、インストーラ、対話操作のどれかを判断する。OSバージョンで利用可能なら4698のClientProcessIdも使う。

4. TaskScheduler Operationalと後続4688で対象Actionの実行有無・結果を確認する。4698だけを実行成功とせず、削除4699や更新4702も調べて短命なタスクを見落とさない。

5. 製品更新・運用ジョブの申請内容、実行者、Action、予定時刻が一致するか確認する。未承認の高権限タスクや不審な後続通信があれば、XML・実体ファイル情報・実行時系列を添えて担当へ引き継ぐ。

### 調査SPL：元イベントの時系列

`REPLACE_...` を検知結果の集約キーに置換します。過去アラートでは `earliest` / `latest` を発生時刻の前後15分の絶対時刻（Unix秒）に変更してください。下記の直近30分は調査開始例です。別ログ種別との照合は対象indexとlog_typeを切り替え、端末IP・host・ユーザーの対応を確認して行います。

```spl
index=detection_lab log_type="windows" host="REPLACE_HOST" earliest=-30m@m latest=now
| sort 0 _time
| table _time host log_type channel event_id TaskName TaskContent SubjectUserName SubjectLogonId ClientProcessId command_line _raw
```

推奨フィールドが未抽出なら `_raw` を参照します。調査SPLは検知条件を再適用せず、同じキーの正常・異常両方を表示します。キー以外の宛先・利用者へ展開する場合は該当セレクタを外して範囲を広げます。

## 限界・見逃す条件

- 特異度：全ての4698に一致する可視化・ハンティング用ルール。ソフト導入の多い端末では件数が増えるため、TaskNameだけの広い除外より署名・Action・所有者の組み合わせを使う。

- 操作範囲：既存タスクの更新4702、タスクファイルやレジストリの直接変更、別経路の永続化はこの式では検知しない。

- 観測の意味：作成は実行・継続動作・SYSTEM昇格を証明しない。Action実行イベントやプロセス作成がなくても、ログ不足と未実行を区別する必要がある。

- ログ品質：4698の収集だけでなくTaskContent XMLの全文保持が調査に必要。XML切り詰めや監査無効、タスク監査の欠損がある環境では登録者と実行内容を復元できない。

共通制約：固定5分窓をまたぐ閾値未満の分散、5分を超える収集遅延、必須フィールド欠損、重複転送の影響を評価してください。Splunk上の実ログ検証・PCRE評価は未実施で、合成テストの成功は本番検知率を示しません。
