# NDR-001 長いDNSラベルを持つ多数の異なる問い合わせ

- 状態：experimental / 重要度：medium
- SIEM：Splunk Enterprise / Splunk Cloud Platform (SPL)
- 対象ログ：ndr

## MITRE ATT&CK Matrix上の位置

|戦術（Matrixの列）|親技法|サブ技法|本ルールとの関係|
|---|---|---|---|
|[TA0011 Command and Control](https://attack.mitre.org/tactics/TA0011)|[T1071 Application Layer Protocol](https://attack.mitre.org/techniques/T1071)|[T1071.004 DNS](https://attack.mitre.org/techniques/T1071/004)|主な検知仮説|

50〜63文字のラベルを含む20種類以上のDNS名をDNSベースC2の探索に用いる。長さと種類数による代理指標で、トンネルや情報持出しの成立は判定しない。

[リポジトリ全体のマトリクス](../matrix.md)。これは技法の一部に対する検知仮説で、技法全体のカバレッジではありません。

## 対象ログ・必要フィールド

- 検知に必須：`_time`, `dns_query`, `log_type`, `protocol`, `src_ip`
- 調査に推奨：`src_ip`, `dest_ip`, `dns_query`, `query_type`, `rcode`, `answers`, `uid`

クライアントを識別できるDNS問い合わせログ。dns_queryを小文字化し末尾ドット除去。

型・元項目・欠損監視は[フィールド定義](../log-sources.md)を参照。推奨項目が未採取の場合は調査結果に制約を記録します。

## 検知条件

`=` は一致、`~=` は正規表現一致、`>=` は以上、`AND` はすべて満たす意味です。`dc()` は異なる値の数です。`~=` は説明・JSON定義の記号で、SPL本文では `match()` に変換します。必須フィールドがNULLなら対象外です。

```text
log_type = "ndr"
AND protocol = "dns"
AND dns_query ~= /(^|\.)[^.]{50,63}(\.|$)/

GROUP BY src_ip
WINDOW = 300 seconds
dc(dns_query) >= 20
```

## 検知SPL（Splunk）

`index=detection_lab` を正規化済みログのindexに変更してください。5分間隔、5分遅延の検索を想定しています。生ログにそのまま適用せず[Splunk導入手順](../deployment.md)でフィールドを確認してください。

```spl
index=detection_lab log_type="ndr" earliest=-10m@m latest=-5m@m
| where isnotnull(_time)
    AND isnotnull(dns_query)
    AND isnotnull(log_type)
    AND isnotnull(protocol)
    AND isnotnull(src_ip)
    AND protocol="dns"
    AND match(dns_query, "(^|\\.)[^.]{50,63}(\\.|$)")
| stats dc(dns_query) as observed min(_time) as first_seen max(_time) as last_seen by src_ip
| where observed >= 20
| eval rule_id="NDR-001", attack_id="T1071.004"
```

## 誤検知とチューニング

CDN、トラッキング、セキュリティ製品。

## 調査手順・判断基準

1. 送信元を固定し、dns_queryの異なる値、問い合わせ時刻、query_type、rcode、answersを取得する。センサーの位置を確認し、src_ipが端末か集約リゾルバかを最初に判別する。

2. 各ラベルの長さ、文字の分布、繰返し、ドメイン別の問い合わせ数を確認する。登録可能ドメインの集約はPublic Suffix List等に基づき、末尾2ラベルだけで機械的に区切らない。

3. 過去7〜14日の同端末・同ドメインと比較し、CDN、AV/EDR、認証サービスの既知パターンか、初観測の長い問い合わせかを確認する。DNS応答コードは補助情報でありNXDOMAINだけを悪性としない。

4. Zeekならuidで接続ログと関連づけ、端末EDRのDNS照会プロセスや後続通信を確認する。複数端末が同じリゾルバに集約されている場合はクライアント側ログで帰属を解決する。

5. 未知プロセス・未知ドメイン・持続的な符号化文字列が重なる場合は問い合わせ一覧と時系列を添えて担当へ引き継ぐ。ログ内のドメインへ能動的に問い合わせたりペイロードを実行したりしない。

### 調査SPL：元イベントの時系列

`REPLACE_...` を検知結果の集約キーに置換します。過去アラートでは `earliest` / `latest` を発生時刻の前後15分の絶対時刻（Unix秒）に変更してください。下記の直近30分は調査開始例です。別ログ種別との照合は対象indexとlog_typeを切り替え、端末IP・host・ユーザーの対応を確認して行います。

```spl
index=detection_lab log_type="ndr" src_ip="REPLACE_SRC_IP" earliest=-30m@m latest=now
| sort 0 _time
| table _time host log_type channel event_id src_ip dest_ip dns_query query_type rcode answers uid _raw
```

推奨フィールドが未抽出なら `_raw` を参照します。調査SPLは検知条件を再適用せず、同じキーの正常・異常両方を表示します。キー以外の宛先・利用者へ展開する場合は該当セレクタを外して範囲を広げます。

## 限界・見逃す条件

- 形状：50〜63文字のラベルを持つ20種類以上の名前のみ。短いラベル、同一名の反復、低速通信、窓を跨ぐ問い合わせは検出できない。

- DNS可視性：暗号化されたDoH/DoTを復号できないセンサー、キャッシュ応答で上流に流れない照会は見えない。FWのDNSポートログだけでは適用できない。

- 帰属：リゾルバ側で複数端末が一つのsrc_ipに集約されると件数が過大になる。端末側の観測点かクライアント情報の補完が必要。

- 特異度：CDNやセキュリティ製品も長い一意ラベルを作る。エントロピー、登録可能ドメイン、応答、プロセスは本検知の条件外であり、DNSトンネルや流出量を断定しない。

共通制約：固定5分窓をまたぐ閾値未満の分散、5分を超える収集遅延、必須フィールド欠損、重複転送の影響を評価してください。Splunk上の実ログ検証・PCRE評価は未実施で、合成テストの成功は本番検知率を示しません。
