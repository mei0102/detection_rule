# WIN-002 Security監査ログの消去

- 状態：experimental / 重要度：medium
- SIEM：Splunk Enterprise / Splunk Cloud Platform (SPL)
- 対象ログ：windows

## MITRE ATT&CK Matrix上の位置

|戦術（Matrixの列）|親技法|サブ技法|本ルールとの関係|
|---|---|---|---|
|[TA0112 Defense Impairment](https://attack.mitre.org/tactics/TA0112)|[T1685 Disable or Modify Tools](https://attack.mitre.org/techniques/T1685)|[T1685.005 Clear Windows Event Logs](https://attack.mitre.org/techniques/T1685/005)|主な検知仮説|

Securityチャネルの1102は監査ログ消去の発生を示すため、Clear Windows Event Logsに直接対応づける。悪意や他チャネルの消去まで保証するものではない。

旧対応：T1070.001。現在の位置を公式STIXデータと照合して更新。

[リポジトリ全体のマトリクス](../matrix.md)。これは技法の一部に対する検知仮説で、技法全体のカバレッジではありません。

## 対象ログ・必要フィールド

- 検知に必須：`_time`, `channel`, `event_id`, `host`, `log_type`
- 調査に推奨：`SubjectUserName`, `SubjectDomainName`, `SubjectLogonId`, `event_id`, `command_line`

Securityチャネルを中央転送し、消去前後の転送欠損を監視。

型・元項目・欠損監視は[フィールド定義](../log-sources.md)を参照。推奨項目が未採取の場合は調査結果に制約を記録します。

## 検知条件

`=` は一致、`~=` は正規表現一致、`>=` は以上、`AND` はすべて満たす意味です。`dc()` は異なる値の数です。`~=` は説明・JSON定義の記号で、SPL本文では `match()` に変換します。必須フィールドがNULLなら対象外です。

```text
log_type = "windows"
AND channel = "Security"
AND event_id = 1102

GROUP BY host
WINDOW = 300 seconds
count(*) >= 1
```

## 検知SPL（Splunk）

`index=detection_lab` を正規化済みログのindexに変更してください。5分間隔、5分遅延の検索を想定しています。生ログにそのまま適用せず[Splunk導入手順](../deployment.md)でフィールドを確認してください。

```spl
index=detection_lab log_type="windows" earliest=-10m@m latest=-5m@m
| where isnotnull(_time)
    AND isnotnull(channel)
    AND isnotnull(event_id)
    AND isnotnull(host)
    AND isnotnull(log_type)
    AND channel="Security"
    AND event_id=1102
| stats count as observed min(_time) as first_seen max(_time) as last_seen by host
| where observed >= 1
| eval rule_id="WIN-002", attack_id="T1685.005"
```

## 誤検知とチューニング

承認済みの保守や検証環境のログ初期化。

## 調査手順・判断基準

1. 1102のhost、発生時刻、SubjectUserName、SubjectDomainName、SubjectLogonIdと原文を保全する。中央転送されたイベントを優先し、元端末だけを証拠の所在にしない。

2. 同じhostの4624をSubjectLogonIdと照合し、実行者のログオン種別と送信元を特定する。LogonIdは別端末間で結合せず、再起動による再利用も考慮する。

3. 消去前後15分の4688、PowerShell 4104、他チャネルのログ消去記録を確認し、GUI操作・管理ツール・スクリプトのどの経路かを調べる。コマンド痕跡がなくても1102を無効としない。

4. 消去前の特権グループ追加、タスク作成、不審ログオンと、消去後のログ到着停止を確認する。Splunkの_indextimeと_timeの差、および端末別の最終到着時刻を確認し、時計ずれ・転送遅延・停止を区別する。

5. 作業申請の対象端末・実行者・時間と照合する。未承認、他の侵害兆候、転送停止が重なる場合は高優先度で担当へ引き継ぎ、消去前に中央保存されたログとタイムラインを添付する。

### 調査SPL：元イベントの時系列

`REPLACE_...` を検知結果の集約キーに置換します。過去アラートでは `earliest` / `latest` を発生時刻の前後15分の絶対時刻（Unix秒）に変更してください。下記の直近30分は調査開始例です。別ログ種別との照合は対象indexとlog_typeを切り替え、端末IP・host・ユーザーの対応を確認して行います。

```spl
index=detection_lab log_type="windows" host="REPLACE_HOST" earliest=-30m@m latest=now
| sort 0 _time
| table _time host log_type channel event_id SubjectUserName SubjectDomainName SubjectLogonId command_line _raw
```

推奨フィールドが未抽出なら `_raw` を参照します。調査SPLは検知条件を再適用せず、同じキーの正常・異常両方を表示します。キー以外の宛先・利用者へ展開する場合は該当セレクタを外して範囲を広げます。

## 限界・見逃す条件

- チャネル制限：Securityの1102のみ。System/Application/PowerShellログの消去や.evtxの直接削除を網羅しない。該当チャネルやファイル監視の別ルールが必要。

- 消去と停止の差：ログサービス停止や監査設定変更だけでは1102が出ない場合がある。イベントがないことを消去なしと解釈せず、最終到着時刻・監査設定変更を別に監視する。

- 証拠の欠落：消去後にForwarderが停止すると中央に1102が到達しない。端末内ログだけの収集は過去の操作を復元できないため、転送状態の監視と中央保存が前提。

- 悪性判定：正規保守でも同じイベントが出る。実行者名だけで例外化せず、申請番号と対象端末・時間を突き合わせる。

共通制約：固定5分窓をまたぐ閾値未満の分散、5分を超える収集遅延、必須フィールド欠損、重複転送の影響を評価してください。Splunk上の実ログ検証・PCRE評価は未実施で、合成テストの成功は本番検知率を示しません。
