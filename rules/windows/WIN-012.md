# WIN-012 作成から5分以内に削除されたタスク

**検知概要：** 作成後5分以内に削除されたスケジュールタスクを探す。

**検知意図：** 一度だけ不正な処理を動かしてタスクを片付けた可能性を調べる。

**過検知予想：** 保守用の一時タスク。 悪性かどうかは、利用目的や実行主体の確認が必要。

|項目|内容|
|---|---|
|対象ログ|Windows Event|
|必要フィールド|`_time`, `log_type`, `channel`, `event_id`, `host`, `TaskName`|
|ATT&CK 戦術|[TA0002 Execution](https://attack.mitre.org/tactics/TA0002), [TA0003 Persistence](https://attack.mitre.org/tactics/TA0003), [TA0004 Privilege Escalation](https://attack.mitre.org/tactics/TA0004)|
|技法 → サブ技法|[T1053 Scheduled Task/Job](https://attack.mitre.org/techniques/T1053) → [T1053.005 Scheduled Task](https://attack.mitre.org/techniques/T1053/005)|
|検索|10分窓／5分間隔／5分遅延|
|工夫|短命なタスクを作成・削除の順序で識別し、同一名の別端末を混同しない。|

## 汎化

- 脅威固有の指標：4698→4699、同一TaskName。
- 共通する実装パターン：短命タスクを作成して痕跡を消す。
- 長期利用できる攻撃行動：作成から5分以内に削除されたタスク。特定攻撃者への帰属は行わない。
- 今回採用する条件と理由：同一端末・同一TaskNameの作成→削除を5分以内で相関する。 この観測範囲で短命タスクを作成して痕跡を消すの候補を抽出するため。
- 採用しない条件と理由：5分超の寿命、削除しないタスクは今回の条件外。別の観測・検知条件が必要なため、この検索に混在させない。未提供の資産台帳による除外も行わない。

## 検知意図と限界

- 検知できること：同一端末・同一TaskNameの作成→削除を5分以内で相関する。
- 検知できないこと：一時タスクを使う保守でも一致。タスクの実行結果は判断しない。
- 意図的に検知しないこと：5分超の寿命、削除しないタスク。
- 想定される回避方法：上記の条件外の経路・表記・タイミングへ変更する、または必要ログの記録を妨げる。

## 誤検知

- 主な正常動作：保守用の一時タスク。
- 誤検知を識別する追加情報：TaskContent、作成者、実行履歴、削除者。
- 改善方法：作成・実行・削除を同一タスクで照合。追加情報が取得できる場合の案で、今回のSPLには未適用。
- 除外が必要な場合の対象と根拠：保守用の一時タスクのうち、上記情報と承認記録で一致を確認した主体・対象・時間帯だけ。現時点の除外はなし。
- 改善により新たに生じる検知漏れ：承認済み主体の侵害を除外する恐れ。追加条件を必須にすると、正常判別用の証拠が欠落した攻撃も見逃す。

## SPL

- 現行SPL：変更前のリポジトリ版（`5d42ac6`）。顧客環境の稼働版ではない。

<details>
<summary>現行SPLを表示</summary>

```spl
index=detection_lab log_type="windows" earliest=-15m@m latest=-5m@m
| where channel="Security" AND event_id IN (4698,4699)
| sort 0 _time
| streamstats time_window=5m current=f
        max(eval(if(event_id=4698,_time,null()))) as created_at
    by host TaskName
| where event_id=4699 AND _time > created_at
    AND _time-created_at <= 300
    AND _time >= relative_time(now(),"-10m@m")
| eval lifetime_seconds=_time-created_at
| table _time host TaskName created_at lifetime_seconds
| eval rule_id="WIN-012", attack_id="T1053.005"
```

</details>

- 提案SPL：検知条件を維持し、ES設定用の出力列を追加。

```spl
index=detection_lab log_type="windows" earliest=-15m@m latest=-5m@m
| where channel="Security" AND event_id IN (4698,4699)
| sort 0 _time
| streamstats time_window=5m current=f
        max(eval(if(event_id=4698,_time,null()))) as created_at
    by host TaskName
| where event_id=4699 AND _time > created_at
    AND _time-created_at <= 300
    AND _time >= relative_time(now(),"-10m@m")
| eval lifetime_seconds=_time-created_at
| table _time host TaskName created_at lifetime_seconds
| eval rule_id="WIN-012", attack_id="T1053.005"
| eval risk_object=host, risk_object_type="system",
       risk_score=40, severity="medium"
```

- 差分：末尾に`risk_object`、`risk_object_type`、`risk_score`、`severity`を追加。検知件数を変える条件変更はなし。列の追加だけではRiskイベント・Notableは生成されない。
- index、sourcetype、製品固有フィールドの置換箇所：`index=detection_lab`は仮置き。実indexと確認済みsourcetypeへ置換し、`log_type`は共通分類を用意するか実ログ条件へ置換。event_id←EventID、channel←Channel、host←Computer。小文字の共通列とXML原文列の対応は各収集方式で要確認。必要列：`_time`, `log_type`, `channel`, `event_id`, `host`, `TaskName`。
- 想定負荷：高（全件ソートと時系列状態を保持するため。データ量・同時実行数による概算で未測定）。
- 負荷を抑える工夫：必要イベントをソート前に絞る。検索窓と並列実行数を制限し、streamstatsの上限を確認。CIM対応と加速済みData Modelが確認できる場合のみtstats化を検討。未提供のData Modelは前提にしない。

## Splunk ES設定案

- 実行間隔：5分（設定案）。
- earliest/latest：`-15m@m` / `-5m@m`。取り込み遅延5分を仮定。
- trigger：結果行数 > 0、各結果行を対象。評価後にRisk Analysis等の応答アクションを別途設定。自動のNotable生成は未設定。
- suppression/throttling：初期は無効。重複実績を確認後、同じrule_id・risk_objectの反復を検索窓相当で抑制する案。別対象・別段階まで抑える可能性があるため宛先等の追加キーを評価。
- severity：`medium`（調査優先度の仮案、確信度ではない）。
- risk score：`40`（未検証の相対値）。繰り返し発報と他ルールとの重複加算を評価してから使用。
- risk object／type：`host` → `risk_object` / `system`。出力に残る主体を使用し、資産・ID正規化と共有IPを確認。
- security domain：`endpoint`。
- notable title：`WIN-012 作成から5分以内に削除されたタスク`。Notable化を採用する場合の案。
- drilldown：結果の`host`を元ログの同じ列へ渡し、検知対象窓の前後5分を再検索。TaskContent、作成者、実行履歴、削除者を表示・照合。未取得の列は追加収集が必要。

## 閾値

- 初期値：同一端末・同一TaskNameの作成→削除を5分以内で相関する。 数値のないイベント・文字列条件は1件一致で結果候補。
- 根拠：上記行動の候補を切り出す設計値。参照ルールの推奨値や実環境の正常分布を証明する値ではない。
- 高感度設定：寿命10分。記載以外の条件は標準と同じ。SPLには未適用。
- 標準設定：提案SPLの条件。初期値と同一。
- 低誤検知設定：寿命2分（検索窓も整合させる）。追加情報が必要な案は取得確認が前提で、効果は未確認。
- ベースライン取得方法：30日を同じ検索窓・集約主体`host`で区切り、正常と確認した保守用の一時タスクとそれ以外を分け、件数・対象数・数値条件の分布を比較。存在しない統計は補完しない。

## 人が評価すべき点

- 採用判断に必要な確認事項：Windows監査設定・対象イベントの欠落、XML項目の抽出状況。TaskContent、作成者、実行履歴、削除者で正常業務と識別できるか。
- 不足データ：実index/sourcetype、必要列の充足率、ESバージョン、発報数・TP/FP判定、資産・業務台帳、実行時間。
- 最大のリスク：保守用の一時タスクとの衝突と、5分超の寿命、削除しないタスクの取りこぼし。
- 推奨判断：実装候補（本番採用の確定ではない）。
- 推奨理由：観測条件を具体化できるため。必須フィールドと正常業務の識別を確認してから採用を判断する。
