# FW-001 単一宛先への多数ポート接続試行

- 状態：experimental / 重要度：medium
- SIEM：Splunk Enterprise / Splunk Cloud Platform (SPL)
- 対象ログ：fw

## MITRE ATT&CK Matrix上の位置

|戦術（Matrixの列）|親技法|サブ技法|本ルールとの関係|
|---|---|---|---|
|[TA0007 Discovery](https://attack.mitre.org/tactics/TA0007)|[T1046 Network Service Discovery](https://attack.mitre.org/techniques/T1046)|なし（親技法に対応）|主な検知仮説|

同じ宛先の20以上のTCPポートへの試行をNetwork Service Discovery候補に対応づける。ポート番号の分散を観測するルールで、サービスの識別や攻撃成功を示さない。

[リポジトリ全体のマトリクス](../matrix.md)。これは技法の一部に対する検知仮説で、技法全体のカバレッジではありません。

## 対象ログ・必要フィールド

- 検知に必須：`_time`, `dest_ip`, `dest_port`, `log_type`, `src_ip`, `transport`
- 調査に推奨：`src_ip`, `dest_ip`, `dest_port`, `action`, `transport`, `src_port`, `session_id`, `packets`, `bytes_in`, `bytes_out`

allow/deny双方のセッションログ。ポートを整数化しNAT前後を区別。

型・元項目・欠損監視は[フィールド定義](../log-sources.md)を参照。推奨項目が未採取の場合は調査結果に制約を記録します。

## 検知条件

`=` は一致、`~=` は正規表現一致、`>=` は以上、`AND` はすべて満たす意味です。`dc()` は異なる値の数です。`~=` は説明・JSON定義の記号で、SPL本文では `match()` に変換します。必須フィールドがNULLなら対象外です。

```text
log_type = "fw"
AND transport = "tcp"

GROUP BY src_ip, dest_ip
WINDOW = 300 seconds
dc(dest_port) >= 20
```

## 検知SPL（Splunk）

`index=detection_lab` を正規化済みログのindexに変更してください。5分間隔、5分遅延の検索を想定しています。生ログにそのまま適用せず[Splunk導入手順](../deployment.md)でフィールドを確認してください。

```spl
index=detection_lab log_type="fw" earliest=-10m@m latest=-5m@m
| where isnotnull(_time)
    AND isnotnull(dest_ip)
    AND isnotnull(dest_port)
    AND isnotnull(log_type)
    AND isnotnull(src_ip)
    AND isnotnull(transport)
    AND transport="tcp"
| stats dc(dest_port) as observed min(_time) as first_seen max(_time) as last_seen by src_ip dest_ip
| where observed >= 20
| eval rule_id="FW-001", attack_id="T1046"
```

## 誤検知とチューニング

脆弱性スキャナ、監視、資産探索。

## 調査手順・判断基準

1. src_ip/dest_ipを固定し、宛先ポート一覧、各ポートの件数、allow/deny、初回・最終時刻を確認する。SYN等のフラグやセッションIDを取得できる場合は、単発試行か確立したセッションかを区別する。

2. 送信元の資産所有者と、当該時刻のNAT変換・DHCP・VPN割当を調べる。共有出口IPの複数利用者を一台のスキャナと扱わない。

3. 脆弱性診断や資産探索の承認範囲・送信元・日時を照合する。既知スキャナでも想定外の宛先や時間なら正常として一括除外しない。

4. 前後30分で同じ送信元の他宛先への試行も確認し、横断・縦断スキャンの広がりを調べる。NDRのアプリケーション識別や応答、サーバ側認証ログで到達後の操作を追う。

5. 未承認の内部端末から多数サービスを探索し、その後に認証・脆弱性悪用の兆候があれば送信元の侵害調査へ進める。遮断だけの場合も対象範囲・継続性を記録し、成功した侵入とは報告しない。

### 調査SPL：元イベントの時系列

`REPLACE_...` を検知結果の集約キーに置換します。過去アラートでは `earliest` / `latest` を発生時刻の前後15分の絶対時刻（Unix秒）に変更してください。下記の直近30分は調査開始例です。別ログ種別との照合は対象indexとlog_typeを切り替え、端末IP・host・ユーザーの対応を確認して行います。

```spl
index=detection_lab log_type="fw" src_ip="REPLACE_SRC_IP" dest_ip="REPLACE_DEST_IP" earliest=-30m@m latest=now
| sort 0 _time
| table _time host log_type channel event_id src_ip dest_ip dest_port action transport src_port session_id packets bytes_in bytes_out _raw
```

推奨フィールドが未抽出なら `_raw` を参照します。調査SPLは検知条件を再適用せず、同じキーの正常・異常両方を表示します。キー以外の宛先・利用者へ展開する場合は該当セレクタを外して範囲を広げます。

## 限界・見逃す条件

- 形状：同一宛先へのTCP縦断探索のみ。多数宛先の同一ポート、UDP、ICMP、20未満の選択的探索や低速探索は対象外。

- 可視性：FW経由の記録しか見えない。同一セグメント内部通信やサンプリング・ログ抑制がある場合、実際のポート数より少なくなる。

- 集計：allow/denyを両方含むため、blockedスキャンも一致する。dc(dest_port)はサービス数や成功セッション数ではない。

- 正規化と時刻：NAT後IPの集約、セッション終了時のみのログ出力、時刻ずれで5分の分布が変わる。検知窓の妥当性を製品のログ出力契機と合わせて評価する。

共通制約：固定5分窓をまたぐ閾値未満の分散、5分を超える収集遅延、必須フィールド欠損、重複転送の影響を評価してください。Splunk上の実ログ検証・PCRE評価は未実施で、合成テストの成功は本番検知率を示しません。
