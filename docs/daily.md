# 日次追加

毎日1件以上を目標に、ATT&CKマトリクスの空欄と対象ログの利用可能性を照合して選びます。
同じ挙動の名前替えやIOCだけの更新は新しいTTPカバレッジとして数えません。

1. 最新mainと日付を確認。当日追加済みなら重複追加を避ける。
2. ATT&CK、SigmaHQ、ESCU、製品公式ログ仕様から観測根拠を調査。参照した資料のタイトル、URL、概要・利用箇所、確認日、版、ライセンスを記録。
3. 公式STIXの戦術ID・名称→親技法→サブ技法を照合し、主な検知仮説と公式の関連列を分ける。新しい技法は固定した一次資料からdata/attack.jsonにも追加し、取得版と差分を記録。
4. 必須項目、記号表記の条件（=、~=、>=）、5分窓・集約キー・閾値、誤検知を揃える。調査は確認フィールド、前後時間、関連ログ、正常判断、引継ぎ条件まで書き、限界は観測範囲・具体的な見逃し・補完ログを示す。
5. 独自JSONと正例・負例を追加。Splunk用の検知SPLと調査SPLをMarkdown本文へ生成し、単独の.splファイルは作らない。相関ルールは閾値直下・窓外・グループ分離も検証。
6. buildと全テストを実行し、生成物の差分を確認。新規ルールはexperimental。Splunkの実行環境がなければその制約を明示する。
7. 通常pushで公開し、コミットと件数を報告。保護ブランチでは作業ブランチをpushして状況を知らせる。force pushをしない。

次の候補：Windows 4104のスクリプト内容、4740との相関、4728の特権グループ追加、NDRのSMB横断接続、Proxyの大容量アップロード。
十分な根拠やテストを用意できない日は無理に追加せず、阻害理由を報告して次回に続けます。
日次実行はCodexのこのタスクのスケジュールで管理します。GitHub Actionsは検証のみで、AI生成や日次追加は行いません。
