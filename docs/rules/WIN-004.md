# WIN-004 ローカルAdministratorsへのメンバー追加

- 状態：experimental / 重要度：medium
- SIEM：Splunk Enterprise / Splunk Cloud Platform (SPL)
- 対象ログ：windows

4732で組み込みAdministratorsのSIDへの追加を観測する。T1098.007のローカルグループ変更に対応し、継続アクセスと権限昇格の両列に位置する。追加された権限の実使用は未検証。

旧対応：T1098。現在の位置を公式STIXデータと照合して更新。

[リポジトリ全体のマトリクス](../matrix.md)。これは技法の一部に対する検知仮説で、技法全体のカバレッジではありません。

## 対象ログ・必要フィールド

- 検知に必須：`_time`, `channel`, `event_id`, `host`, `log_type`, `target_sid`
- 調査に推奨：`TargetSid`, `target_sid`, `MemberSid`, `MemberName`, `SubjectUserName`, `SubjectLogonId`, `event_id`

Audit Security Group Management Success。TargetSidは追加先グループのSID。

型・元項目・欠損監視は[フィールド定義](../log-sources.md)を参照。推奨項目が未採取の場合は調査結果に制約を記録します。

## 検知条件

`=` は一致、`~=` は正規表現一致、`>=` は以上、`AND` はすべて満たす意味です。`dc()` は異なる値の数です。`~=` は説明・JSON定義の記号で、SPL本文では `match()` に変換します。必須フィールドがNULLなら対象外です。

```text
log_type = "windows"
AND channel = "Security"
AND event_id = 4732
AND target_sid = "S-1-5-32-544"

GROUP BY host
WINDOW = 300 seconds
count(*) >= 1
```

## 検知SPL（Splunk）

`index=detection_lab` を正規化済みログのindexに変更してください。5分間隔、5分遅延の検索を想定しています。生ログにそのまま適用せず[Splunk導入手順](../deployment.md)でフィールドを確認してください。

```spl
index=detection_lab log_type="windows" earliest=-10m@m latest=-5m@m
| where isnotnull(_time)
    AND isnotnull(channel)
    AND isnotnull(event_id)
    AND isnotnull(host)
    AND isnotnull(log_type)
    AND isnotnull(target_sid)
    AND channel="Security"
    AND event_id=4732
    AND target_sid="S-1-5-32-544"
| stats count as observed min(_time) as first_seen max(_time) as last_seen by host
| where observed >= 1
| eval rule_id="WIN-004", attack_id="T1098.007"
```

## 誤検知とチューニング

承認された権限付与。

## 調査手順・判断基準

1. 4732のTargetSid=S-1-5-32-544を原文で確認する。MemberSid/MemberNameは追加された主体、SubjectUserName/SubjectLogonIdは追加操作の実行者として分けて記録する。

2. MemberSidを当該時点のディレクトリ・端末情報で解決し、利用者・コンピュータ・グループのどれかを識別する。グループの場合はネストされたメンバーと実効権限への影響を確認する。

3. 操作したSubjectLogonIdと同じhostの4624、4688を照合し、対話操作か構成管理による変更か、送信元が正規踏み台かを確認する。

4. 追加された主体の後続ログオンと4672、サービス・タスク作成を確認する。削除4733が直後にあっても権限利用がなかったとは限らないため、追加から削除までの操作を追う。

5. 権限申請、所有者、付与期限と照合する。未承認追加なら追加主体・操作主体・影響端末・利用証跡をまとめて権限管理担当へ引き継ぎ、既存の手順で取消可否を判断する。

### 調査SPL：元イベントの時系列

`REPLACE_...` を検知結果の集約キーに置換します。過去アラートでは `earliest` / `latest` を発生時刻の前後15分の絶対時刻（Unix秒）に変更してください。下記の直近30分は調査開始例です。別ログ種別との照合は対象indexとlog_typeを切り替え、端末IP・host・ユーザーの対応を確認して行います。

```spl
index=detection_lab log_type="windows" host="REPLACE_HOST" earliest=-30m@m latest=now
| sort 0 _time
| table _time host log_type channel event_id TargetSid target_sid MemberSid MemberName SubjectUserName SubjectLogonId _raw
```

推奨フィールドが未抽出なら `_raw` を参照します。調査SPLは検知条件を再適用せず、同じキーの正常・異常両方を表示します。キー以外の宛先・利用者へ展開する場合は該当セレクタを外して範囲を広げます。

## 限界・見逃す条件

- 対象グループ：組み込みAdministratorsのSIDだけを検知。Remote Desktop Users、Domain Admins、他のローカル特権グループの変更は検知しない。名前の翻訳差にはSID指定で対応する。

- イベント種別：4728/4756など別のグループ種別や既存グループのネスト変更による実効権限増加は対象外。T1098.007全体をカバーするものではない。

- 採取：Audit Security Group Managementの成功監査が無効だと記録されない。ドメインコントローラのdomain localグループでは資産の役割も確認し、一般端末のローカルグループと同一視しない。

- 意図と効果：正規配布ツールも同じ変更を行う。追加イベントだけでは権限を使ったか・申請済みかは分からず、MemberSid解決と承認情報が必要。

共通制約：固定5分窓をまたぐ閾値未満の分散、5分を超える収集遅延、必須フィールド欠損、重複転送の影響を評価してください。Splunk上の実ログ検証・PCRE評価は未実施で、合成テストの成功は本番検知率を示しません。
